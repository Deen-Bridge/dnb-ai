# Quran reference data — provenance

## `surah_index.json`

Generated by [`scripts/build_surah_index.py`](../../scripts/build_surah_index.py).

**Version:** `surah_index` data version `1.0.0` (recorded in the build script's
output header and in the service's data manifest). Any change to the contents
of this file requires a version bump and a corresponding entry in the changelog
below.

**Contents:** for each of the 114 surahs — number, transliterated name, Arabic
name, revelation place, ayah count, and common alternative spellings.

**Deliberately absent:** any Quranic text. This file is a *reference table*, not
a mushaf. Its only job is to let the service answer "is `2:300` a real ayah?"
offline, so an invalid reference is rejected before any network call and long
before a model has the chance to invent a verse.

**Numbering:** the Kufan count (6236 ayat in total), which is the numbering used
by the Uthmani mushaf, by Quran.com, and by every tafsir source this service
reads. The build script asserts both the surah count (114) and the total ayah
count (6236), so a typo in the table fails the build rather than shipping a
wrong bound.

**Uncertainty:** alternative spellings are curated conveniences, not an
authoritative transliteration standard. Transliterated names may vary between
scholarly traditions; lookups must match on surah number, not on name alone.

**Licensing:** surah names and ayah counts are facts about the mushaf, not a
creative work, and carry no copyright.

**Reproducibility:** running `scripts/build_surah_index.py` on the same
script revision produces byte-identical output. The reviewer can verify the
counts without any secrets or network access.

## Ayah text and translations

Not bundled. Arabic text (`text_uthmani`) and translations are fetched at
request time from the [Quran.com API v4](https://api-docs.quran.com/) and cached
per ayah — see `tafsir.py`. Nothing is stored on disk.

Cached entries are keyed by surah, ayah, and resource identifier, and carry the
fetch timestamp. Cache entries are user-independent and contain no personal data,
so they are not subject to per-user reset; they can be purged globally without
affecting any user's stored state.

## Tafsir text

Not bundled. Tafsir text is fetched per ayah from the same API, which serves the
works listed in `TAFSIR_REGISTRY` (`tafsir.py`). Attribution — the work's name,
author, and language — always comes from the API's own response for the resource
that was fetched; this service never labels a block of tafsir text from its own
memory of who wrote what.

When the upstream API is unavailable or returns no content for a requested
resource, the service reports the item as unavailable with provenance intact
rather than substituting content from another source or from model memory.

## Operational notes

- **Configuration:** the Quran.com API base URL and timeout are read from service
  configuration; no API credentials are required for the public endpoints used.
- **Failure modes:** an invalid surah/ayah reference is rejected offline against
  this index. Network failures or empty upstream responses return an explicit
  unavailable state, never fabricated text.
- **Observability:** fetch successes, cache hits, and upstream failures are
  logged with surah/ayah identifiers only; no request payloads containing user
  content are logged.
- **Rollback:** the index is a static file. Reverting to a prior version is a
  file revert plus redeploy; no migration is required. Cached upstream entries
  remain valid across a rollback because they are keyed by resource identifier.
